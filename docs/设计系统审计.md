# ThaiAI 设计系统审计

> 审计日期：2026-09-27 ｜ 范围：`src/` + `backend/` 共 221 个源文件 ｜ **只读，未改动任何产品代码**
> 度量脚本：`node scripts/audit-design-system.mjs`（`--json` 可进 CI），所有数字可由该脚本复现。

## 方法

借两套公开设计系统的方法论，因为它们解决的问题和 ThaiAI 现在的问题同类：

| 来源 | 借用的判断标准 | 用在本次审计的哪一层 |
|---|---|---|
| **IBM Carbon** | token 分三层 **primitive → semantic → component**；语义层必须是单一事实来源，组件不得自带原始色值 | 第 1、2 层 |
| **GOV.UK Design System** | pattern 优先：同类交互（错误、加载、空态、表单校验）全站只能有**一个共享实现**；文案是设计的一部分 | 第 3、4 层 |

## 一页结论

1. **你的问题不是"没有设计系统"，而是"有三套半，且互不知道对方存在"**：`src/index.css` 的 CSS 变量、`src/themes/theme.css` 的 `--tp-*`/`--gv-*`/`--acc-*` 命名空间、`themes/worlds.js` 的 JS token 对象；外加后端 10 处各写各的 AI 人格。四者没有共同源头。
2. **token 覆盖率只有 26%**（`var(--…)` 583 处 vs 硬编码颜色 1656 处），全仓有 **261 个不同色值**——远超声学上一个系统应有的 40–60 个语义色。前 8 个高频硬编码色就是事实上的语义色，只是没名字。
3. **组件层采用率 20%**（105 个渲染 UI 的文件里只有 21 个用过 `@/components/ui/*`），业务代码手搓 `<button>` **456 处**。这正是你 `fix/light-mode-surfaces` 分支改动量巨大、且容易反复漏改的直接原因。
4. **最能立刻见效的是 Voice & Tone**：`backend/contextPrompts.js:69` 那套提示词已经写得很专业（禁止编造数据、不确定就写"需要更多上下文"、区分"语法正确/自然/适合关系"、用 Very Natural 这类定性表述），但这条质量线**只有它自己在守**，其余 9 处人格声明没有继承。
5. **两个我一开始怀疑、测完确认"不是问题"的地方**（避免误伤）：`.dark` 只缺 6 个字体/圆角变量且都能从 `:root` 继承，明暗一致性没有缺口；Radix 系组件（dialog/select/sheet/accordion/toast）源码里没有 `aria-*` 是正常的，无障碍由 Radix 内部提供。

## 1. Token 层

### 1.1 三个平行的 token 事实来源

| 来源 | 形态 | 证据 | 问题 |
|---|---|---|---|
| `src/index.css` | CSS 变量，`:root` 46 个 / `.dark` 40 个 | 全仓 583 处 `var(--…)` | 主命名空间，但没有分层：`--brand-green` 和 `--text-muted` 平级 |
| `src/themes/theme.css` | 18 个**全新命名**的变量 | `--tp-bg` `--tp-text` `--tp-primary` `--tp-accent` `--tp-glow`… `--gv-bar` `--gv-active`… `--acc-ease` `--acc-expand`… | 第二套命名空间；这些"组件级 token"直接存原始色值，而不是指向语义 token |
| `src/themes/worlds.js` + `components/world/*` | JS 里的颜色/字体对象 | `worlds.js` 65 处硬编码色、**0 处** `var()`；`deepSpace.js` 62 处、0 处 | 第三套：JS 侧的并行 token 表，CSS 变量改不动它 |

`themes/course-paper.css`、`themes/vocab-paper.css` 定义 0 个变量（纯硬编码样式表，共 1586 行）；`world-shim.css` 覆盖 14 个 index.css 同名变量（这是有意的主题重映射层，`useWorldThemeIsolation` 会按需摘掉它，属设计而非缺陷）。

### 1.2 覆盖率与"事实语义色"

```
token 覆盖率        26%   （583 var 引用 ÷ 2239 次颜色用法）
不同色值            261 个
硬编码颜色          1656 处
```

出现次数最多的硬编码色，就是**最该先命名的语义 token**：

| 色值 | 次数 | 它实际承担的角色（据出现的上下文归纳） |
|---|---|---|
| `#e8c684` | 45 | 强调金（章节编号、金色点缀、登录页 italic 标题） |
| `#182c41` | 34 | 深墨色文字（浅底场景的主文字） |
| `#6ee7a8` | 29 | 成功/正向反馈（薄荷绿） |
| `#050807` | 25 | 最深背景（沉浸场景底色） |
| `#cb8dff` | 24 | 强调紫（世界/成就体系） |
| `#fffcf5` | 21 | 纸白底（浅色"纸感"主题） |
| `#1d1d1f` | 21 | Apple 式墨色（毛玻璃导航条） |
| `#0b7a5a` | 16 | 品牌绿（主 CTA/链接） |

### 1.3 重灾区：世界/沉浸层

`themes/`、`components/world/`、`lib/world*`、落地页合计：**硬编码 824 处 vs token 375 处**。也就是说 token 覆盖率在业务 UI 里还行，在 3D/沉浸层基本失效——而这一层恰恰是视觉最重的部分，改主题时最容易失控。

### 1.4 明暗一致性（结论：无需处理）

`.dark` 比 `:root` 少 6 个：`--radius`、`--font-heading/body/display/mono/thai`。这些属于"不随明暗变化"的全局量，从 `:root` 继承是正确做法。**不要把这条列进待办**。

### 1.5 修法（Carbon 三层落地到你的仓库）

```
第 1 层 primitive（只在这里写色值）
  --thai-ink-900: #182c41;  --thai-gold-500: #e8c684;  --thai-mint-400: #6ee7a8; …

第 2 层 semantic（组件只许引用这一层）
  --color-text-primary: var(--thai-ink-900);
  --color-accent:       var(--thai-gold-500);
  --color-success:      var(--thai-mint-400);
  --color-surface:      var(--thai-paper-000);

第 3 层 component（可选，命名空间照现在保留）
  --tp-bg: var(--color-surface);   ← 把 theme.css 里的原始色值改成指向语义层
```

迁移顺序（**不要一次性全量替换**）：

1. 先只做**新增语义别名**（纯加法，零风险）：把上表 8 个高频色值补成语义 token，`index.css` 追加一段，不动任何现有代码。
2. 把 `themes/theme.css` 的 18 个 `--tp-*`/`--gv-*`/`--acc-*` 的值改成 `var(--color-*)`（一次一个组件区块，肉眼可验证）。
3. `themes/worlds.js` 从"颜色对象"改为"引用语义 token 名的映射表"，让 JS 与 CSS 指向同一份定义。
4. 最后才逐页把硬编码替换成 var()，用脚本复测覆盖率（目标：26% → 60%+，色值数 261 → < 100）。

## 2. 组件层

### 2.1 采用率

```
渲染 UI 的业务文件        105 个，其中引用 @/components/ui/* 的 21 个（20%）
业务代码手搓 <button>      456 处
业务代码手搓 <input>       39 处
```

**影响**：每一次视觉改版（比如你正在做的浅色化）都要在这 456 处里找，而不是改 1 个 `Button` 的 variant。这不是"代码不优雅"，而是**改动成本和回归风险**的直接来源。

### 2.2 组件状态矩阵（13 个 `.jsx`；6 个 `.d.ts` 已排除）

| 组件 | focus-visible | disabled | aria-* | CVA variants |
|---|---|---|---|---|
| button.jsx | ✓ | ✓ | 0 | ✓ |
| toggle.jsx | ✓ | ✓ | 0 | ✓ |
| label.jsx | — | ✓ | 0 | ✓ |
| sheet.jsx / toast.jsx | — | ✓ | 0 | ✓ |
| input.jsx | — | ✓ | 0 | — |
| select.jsx / dialog.jsx | — | ✓ | 0 | — |
| accordion.jsx / premium.jsx | — | —/✓ | 2 | — |

`aria-*` 一栏为 0 的多数是 Radix 封装（无障碍由 Radix 提供，**不算缺陷**）。真正需要补的是自研组件（`premium.jsx`、`matrix-orb.jsx`）与 `input.jsx` 的 `focus-visible`。

### 2.3 焦点可达性（实测只有 1 个真问题）

初次扫描显示 12 个文件"有 `outline-none` 且无 focus-visible"，逐一核对后**只有 1 个真的没有替代反馈**：

- `src/pages/Vocabulary.jsx:692`——搜索框 `className="… text-white outline-none placeholder:text-white/25"`，键盘 Tab 进来完全看不到焦点。

其余文件用的是 `focus:ring` / `focus:border` / `focus-within:`，属正常做法。**结论：这条不是系统性问题，修 1 处即可。**

### 2.4 修法

不做"全量替换 456 个 button"（收益/风险比差）。改为：

1. **闸门**：在 `AGENTS.md` 里加一条——新增 UI 必须用 `@/components/ui/*`，除非在 PR 描述里说明理由。
2. **顺手替换**：每个功能迭代碰到哪个页面，就把该页的 button 换成 `<Button variant=…>`；用 `grep -c '<button'` 作为收敛指标（脚本里已包含）。
3. **补 variant**：先确认 `button.jsx` 的 variant 覆盖现有 456 处的主要形态（观察到的至少有：主 CTA、幽灵按钮、图标按钮、危险操作、表格行内小按钮），缺的补进去——**否则第 2 步会被迫继续手搓**。

## 3. Pattern 层（GOV.UK 口径）

### 3.1 同类交互的重复实现

| 模式 | 出现文件数 | 出现次数 | 判断 |
|---|---|---|---|
| 错误提示（`text-red-*` / 自定义红） | 29 | **156** | 无共享组件：颜色、位置、是否带图标全靠各页自觉 |
| 加载动画 `animate-spin` | 29 | 59 | 无"什么时候用 spinner、什么时候用骨架"的规则 |
| 空状态文案（暂无/还没有…） | 32 | 54 | 无统一结构（缺"下一步该做什么"的引导） |
| 骨架屏 `animate-pulse` | 17 | 40 | 见上 |
| 自建弹层 `fixed inset-0` | 15 | 19 | `dialog.jsx`/`sheet.jsx` 已存在但未被复用 |
| toast 调用 | 4 | 10 | 已有 sonner，属于少数已收敛的模式 ✓ |

### 3.2 缺失的 pattern（GOV.UK 一定有、你这里没有）

1. **错误摘要（error summary）**——表单提交失败时，顶部汇总 + 锚点跳到第一个错误字段；现在 156 处错误提示都是散落的单点文本。
2. **字段级错误**——`input.jsx` 没有 `error` prop 与 `aria-invalid`/`aria-describedby` 连接（`aria-*` 计数为 0）。
3. **空状态的固定结构**——标题 + 一句解释 + 一个主行动（现在 54 处多数只有一句"暂无…"）。
4. **加载态的选择规则**——>300ms 才显示、列表用骨架、按钮内用 spinner、页面切换用顶部进度。当前 99 处加载实现没有这条规则。
5. **破坏性操作确认**——删除/重置类操作缺少统一确认 pattern。

### 3.3 修法

在 `src/components/ui/` 下新增 `patterns/`（3 个起步，先做最常用的）：

```
patterns/FormError.jsx    错误摘要 + 字段级错误（含 aria-invalid/aria-describedby）
patterns/EmptyState.jsx   标题 + 说明 + 主行动
patterns/Loading.jsx      spinner / skeleton / inline 三种形态 + 何时用哪种的注释规范
```

配套写一页 `docs/交互模式.md`：每个 pattern 写清"何时用、何时不用、无障碍要求"。GOV.UK 的价值就在这页文档，而不是组件本身。

## 4. Voice & Tone 层

### 4.1 后端有 10 处人格声明、至少 5 套口径

| 文件:行 | 自称 |
|---|---|
| `backend/routes/aiTeacher.js:377` | AI 泰语老师「阿泰」的记忆系统 |
| `backend/routes/aiTeacher.js:445` | ThaiAI 的 AI 泰语发音老师 |
| `backend/routes/aiTeacher.js:457` | ThaiAI 的 AI 泰语口语陪练老师，性格亲切、像朋友一样 |
| `backend/routes/aiTeacher.js:537 / 591` | ThaiAI 的 AI 泰语老师「阿泰」 |
| `backend/routes/aiTeacher.js:506` | （角色扮演）餐厅服务员 |
| `backend/contextPrompts.js:69` | Thai Context Intelligence 专家 |
| `backend/translate.js:36 / 131` | 资深泰语教学专家 |
| `backend/routes/thai.js:133` | 泰语词典（无人格） |

同一个产品，学生对面的"老师"有时叫阿泰、有时是"专家"、有时是一本词典。**这是 Voice & Tone 的单一事实来源缺失**，也解释了为什么同一个功能在不同入口的语气会飘。

### 4.2 唯一写得专业的那一套，应该升级成全局规范

`backend/contextPrompts.js:69` 已经包含一条真正的质量线，值得被所有 AI 功能继承：

- 不只给字典翻译，要说明泰国人什么时候说、对谁说、听起来什么感觉
- 严格区分"语法正确 / 自然 / 适合当前关系"
- **没有真实语料时不要编造百分比、排名**，改用 `Very Natural / Natural in context / Needs context` 定性表述
- 不确定时明确写"需要更多上下文"，不猜

其余 9 处人格声明**没有继承任何一条**。对教学产品来说，这条线守不守得住，直接等于"老师靠不靠谱"。

### 4.3 缺失项

1. **称呼与自称统一**（阿泰 / 老师 / 专家 / 词典）。
2. **纠错语气分级**：发音错、语域错（对长辈用随意说法）、文化错，三种错误的措辞强度应当不同——现在只有零散的"语气亲切专业""鼓励为主"。
3. **回答结构不统一**：`aiTeacher.js:448-453` 用【音节划分】【罗马音】【中文近似音】… 六段；`contextPrompts.js:84+` 用【你的表达】【核心意思】【Native Feeling】【场景与关系】… 另一套。学生看到的版面随入口变化。

### 4.4 修法

```
backend/persona.js        ← 唯一来源：PRODUCT_VOICE（称呼、自称、鼓励/纠错分级）
                            + QUALITY_RULES（直接搬 contextPrompts.js:69 那套）
                            + ANSWER_SHAPES（按任务类型定义小节结构）
各 route 改为 persona.compose("pronunciation", { learner, scene })
```

工作量：**M**（半天到 1 天），但收益是"老师"这个核心体验的一致性——对这个产品比换任何 UI 组件都值。

## 七、明确不建议做的

- **不要引入第二套组件库**（Mantine/Chakra/Semi/Ant）——你已有 shadcn + Radix + CVA + cmdk + sonner，再叠一套只会让 456 处手搓变成两套并存。
- **不要为对齐 Carbon 而重命名 46 个现有变量**——迁移成本高、视觉零收益；用"新增语义别名 + 逐步指向"的方式收敛即可。
- **不要追求 100% token 覆盖率**——3D/沉浸层有大量仅在 WebGL/Canvas 内使用的颜色，留在代码里更合理；目标是业务 UI 60%+，色值数降到 100 以内。
- **不要删 `world-shim.css`**——它是有意的主题重映射层，且 `useWorldThemeIsolation` 依赖它。
